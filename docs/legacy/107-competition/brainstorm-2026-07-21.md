# 第二轮自由发散：独立候选方向

日期：2026-07-21

本轮目标不是排名，而是扩大候选空间。以下想法基于赛事官方赛道边界、团队学科构成与用户侧可获得的 107 能力生成；尚未做竞品检索、完整技术验证或评委 scorecard。

## 0. 既有四项编号

- **A｜107 使用体验整合平台**：把 SSH、SFTP、Slurm CLI、日志、文件与资源信息整合为可视化入口。
- **B｜可复现实验档案馆 + checkpoint 恢复**：保存应用级 checkpoint，并绑定代码、环境、参数、数据与结果。
- **E｜持久计划 / 任务图 / anti-drift 系统**：把复杂任务表示为可版本化、可审查、可 replay 的任务—证据图，再交给 Agents 执行。
- **F｜“我的科大”个人校园 Agent**：跨 USTC 网站检索并组织校园信息，以自然语言提供服务导航。

编号只用于引用，不表示优先级。

# 一、算力平台赛道：新增方向

## C1｜RunPack：本地项目到 107 的迁移打包器

**核心想法**

用户给出一个本地 Python / PyTorch / Jupyter 项目，工具生成并验证一份可在 107 上运行的 RunPack：

- 依赖与硬件需求探测；
- 环境锁定；
- 数据上传清单；
- Slurm 脚本；
- 预检与小规模 smoke；
- 正式运行；
- 结果回收与运行报告。

**为什么与 A 不同**

A 是通用操作前端；RunPack 聚焦“把一个项目可靠迁入 107”这一条完整旅程。它可以先做 CLI/Web wizard，不必建设三端管理平台。

**最小演示**

同一个公开 PyTorch 项目：本地导入 → 自动生成 RunPack → 107 小样本 smoke → GPU 正式运行 → 下载结果和 provenance report。

**价值**

降低新用户第一次把课程或科研项目迁到 HPC 的成本，直接对应官方“课程实验迁移与加速实践”。

**主要风险**

依赖组合千变万化。首版必须限定 Python/PyTorch、Conda 或容器中的一种环境模型。

## C2｜Pilot-to-Scale：资源规格校准器

**核心想法**

不依赖平台全局历史数据，而是先替用户运行一个小规模 pilot，测量：

- GPU/CPU 利用率；
- 峰值显存和内存；
- I/O；
- 每 step 时间；
- 数据规模与运行时间的经验关系。

再给出资源规格、预计时长、checkpoint 间隔和 Slurm 参数建议。

**为什么与“绿色算力规划”不同**

绿色规划依赖全平台队列、能耗和节点数据；本方向只用用户自己任务的可观测数据，权限风险更低。

**最小演示**

对三个有不同资源特征的任务，比较用户盲填资源与 Pilot-to-Scale 推荐：OOM 率、浪费率、估时误差和成功率。

**潜在亮点**

它不是通用聊天式“资源建议”，而是一套 measurement-first 的实验协议。

**主要风险**

小样本外推可能失真；必须报告置信区间、适用范围和拒绝给建议的条件。

## C3｜SweepLab：并行参数实验与自适应采样平台

**核心想法**

面向需要大量重复实验的课程、科研和竞赛任务，用户声明：

- 参数空间；
- 单次运行命令；
- 指标提取规则；
- 预算与停止条件。

系统在 107 上生成 Slurm array 或多批作业，收集结果并可选地使用 Bayesian optimization、successive halving 或 bandit 策略减少无效实验。

**团队契合点**

Develata 可负责概率统计、实验设计、不确定性和停止规则；AI/CS 成员负责调度、执行与可视化。

**最小演示**

选一个公开机器学习任务和一个随机模拟任务，比较 grid search 与自适应采样在同等算力预算下找到优良参数的效率。

**主要风险**

容易退化成“又一个超参优化框架”。差异必须来自 107 workflow、可复现实验记录和用户友好的预算/停止语义。

## C4｜RandomLab 107：随机系统与相变实验室

**核心想法**

将随机图、渗流、分枝过程、Monte Carlo 或统计物理模型做成可复现实验应用：

- 用户选择模型与参数区域；
- 107 并行运行大量样本；
- 在线汇总经验分布、临界现象与有限尺寸效应；
- 自动记录随机种子、代码、环境和误差；
- 输出可用于课程或科研探索的实验报告。

**为什么算力必要**

重点不是动画，而是大规模 ensemble、罕见事件估计、参数扫描与不确定性量化；普通动画只是结果呈现层。

**最小演示**

例如对 Erdős–Rényi 随机图在临界窗口附近运行大规模实验，展示最大连通分量的尺度变化与有限样本偏差。

**潜在价值**

学科辨识度强，能体现数学、AI 和计算机成员的组合，而不是复刻官方工具题。

**主要风险**

产品受众比平台工具窄；必须把课程教学、实验复现或科研探索中的真实使用方式讲清楚。

## C5｜FailureGym：HPC 作业故障诊断与恢复训练场

**核心想法**

提供一组可控故障场景：OOM、依赖缺失、路径错误、GPU 不可见、时间上限、I/O 瓶颈、节点中断。系统：

1. 运行故障 fixture；
2. 捕获日志和资源轨迹；
3. 给出结构化故障证据；
4. 让用户选择或生成修复；
5. 重跑验证修复是否真的生效。

**与算力平台 Agent 的区别**

不是只让 LLM 阅读错误文本，而是有真实 fault injection、可重复实验和修复后验证。

**最小演示**

五类典型作业从失败到定位再到通过，展示误诊率、恢复时间和验证证据。

**主要风险**

需要安全地限制故障范围，不能影响其他用户或平台节点。

## C6｜Artifact Relay：大型实验数据的增量同步与可验证交付

**核心想法**

解决数据和结果在本地、107 用户目录、对象存储之间移动时的痛点：

- 内容寻址与分块；
- 增量上传/下载；
- 断点续传；
- 压缩策略；
- manifest 与 checksum；
- 数据来源和结果 lineage。

**与 A 的区别**

不是通用文件管理 GUI，而是面向大实验资产的可靠传输和 provenance protocol。

**最小演示**

故意中断一次大文件传输，恢复后证明只补传缺块且最终 manifest 完全一致。

**主要风险**

若实际比赛环境已有成熟工具且痛点不明显，产品价值会削弱；需先访谈真实用户。

# 二、智能体赛道：新增方向

## G1｜科大办事导航 Agent：从“我要做什么”到可验证流程

**核心想法**

不做“什么都能问”的泛校园助手，而是聚焦办事流程。用户提出目标：

- 申请 107 SSH；
- 申请东风云虚拟机；
- 找某类课程/实验室/竞赛；
- 办理一个具体校内事项。

Agent 输出带来源、前置条件、截止时间、联系人和失败边界的步骤清单。

**核心技术点**

- 官方来源优先级；
- 时间有效性；
- 多页面信息合并；
- 冲突检测；
- 引用与抓取时间；
- 不确定时拒绝编造。

**最小演示**

选 10–20 个真实校园流程，建立人工 gold answer；对比普通搜索/RAG 与流程 Agent 的完整率、时效性和引用正确率。

**为什么可能强于 F**

它把 F 的广泛愿景收窄为一个可评测、高价值的用户旅程。

## G2｜USTC ChangeRadar：校园规则与机会变更监测 Agent

**核心想法**

持续监测教务处、院系、网络信息中心、基金/竞赛、讲座等公开页面，识别：

- 新通知；
- 截止时间变化；
- 规则修订；
- 新附件；
- 联系方式或资源变化。

再按用户兴趣生成带 diff 和来源的个性化更新，而不是简单 RSS 转发。

**最小演示**

以“一〇七杯”通知与后续 FAQ 为例：主通知表面写“一队一赛道”，后续 FAQ 澄清一人可跨两赛道、同队需不同作品。Agent 应发现并解释这种更新，而不是机械重复旧文本。

**亮点**

当前比赛本身就提供了一个真实、可讲述的冲突/更新案例。

**主要风险**

需要处理网页结构变化、重复通知和用户兴趣冷启动。

## G3｜Campus Opportunity Graph：校园机会匹配与路径规划

**核心想法**

把课程、科研项目、讲座、竞赛、实习、奖学金、算力资源等组织成带前置条件和时间窗口的机会图。Agent 根据用户背景与目标提出：

- 当前可参加的机会；
- 缺失前置条件；
- 时间冲突；
- 一条可执行的准备路径。

**与普通推荐系统的区别**

不仅推荐条目，还解释资格、依赖、时序和来源，并允许用户校正画像。

**最小演示**

面向新生、升学学生和科研入门学生各设计一组任务，评价资格过滤准确率和计划可执行性。

**主要风险**

个人画像涉及隐私；首版应由用户显式提供最小信息，不擅自抓取学籍或成绩。

## G4｜Spec-to-Evidence Workbench：从需求到证据的 Agent 协作台

**核心想法**

这是对 E 的进一步具体化。核心对象不是“更长的 prompt”，而是 typed graph：

- Goal；
- Assumption；
- Task；
- Dependency；
- Acceptance criterion；
- Evidence；
- Decision；
- Revision。

Agent 只能领取满足依赖的节点；输出必须附 evidence；修改上游假设后，系统标出受影响节点并要求 replay 或人工豁免。

**最小演示**

让普通一次性 plan 与 Workbench 分别完成一个会在中途暴露新约束的任务，对比：偏离目标次数、无证据完成声明、返工范围和人工恢复成本。

**为什么不只是 workflow skill**

Skill 是行为提示；Workbench 提供持久状态、类型约束、依赖传播和可测量的执行语义。

**主要风险**

若没有强实验设计，很容易被评委看成看板 + prompt orchestration。

## G5｜Decision Ledger：把群聊转成可追溯的团队决策

**核心想法**

面向学生项目组、课程小组和社团：Agent 从群聊中提取但不擅自决定：

- 候选方案；
- 各方观点；
- 假设与证据；
- 真正分歧；
- 已形成共识；
- 待确认事项；
- 后续决策变化。

成员确认后才写入 append-only decision ledger。新讨论与历史决策冲突时，Agent指出具体冲突。

**来源于真实需求**

`ezhuman` 的群聊助手 prompt 已经是自然原型；本项目可把“总结对话”提升为有确认语义的决策系统。

**最小演示**

用脱敏的项目讨论 fixture 测试：观点归属准确率、未确认内容误写为共识的比例、冲突召回率和成员修订成本。

**主要风险**

隐私、群聊平台接入和说话人归属；首版可只接受用户上传的脱敏记录。

## G6｜SourceCourt：多来源冲突裁决与时效性 Agent

**核心想法**

专门解决校园信息中“多个官方页面说法不同”的问题。多个 subagents 分别：

- 找 primary sources；
- 识别发布时间与最后修改时间；
- 提取精确断言；
- 比较适用对象和生效时间；
- 给出可解释的当前结论或明确保持 unresolved。

**最小演示**

构造或收集 20 组校园规则冲突案例，评估它能否避免“取第一条搜索结果即回答”。

**与 G1/G2 的关系**

它可以独立成为可信信息 Agent，也可以成为办事导航和 ChangeRadar 的核心 verifier。

**主要风险**

单独作为产品可能过窄；需要一个用户可感知的场景承载。

## G7｜Campus Research Onboarding Agent：科研入门路径助手

**核心想法**

学生输入研究兴趣、课程背景和可投入时间，Agent 联合检索：

- 校内相关教师与实验室公开主页；
- 课程、讲座与讨论班；
- 107/词元/数据库等研究资源；
- 入门教材和公开资料；
- 可执行的四周或八周探索计划。

**团队契合点**

团队跨数学、AI、计算机和少年班学院，能够从不同阶段学生的真实体验校准系统。

**最小演示**

选随机图、计算机视觉和系统方向，邀请少量同学评价路径相关性、来源准确性和可执行性。

**主要风险**

不能把公开主页信息推断成导师当前招生意愿；必须清楚区分事实与建议。

# 三、反常规组合方向

以下不是建议联动两个参赛作品，而是通过组合两个机制产生新产品。

## X1｜实验契约编译器

用户不直接写 Slurm 脚本，而是声明实验契约：数据、代码、资源上限、随机性、checkpoint、输出与验收指标。系统将契约编译成 107 RunPack，并在结束后验证产物是否满足契约。

它结合 C1、C2、B，但价值中心是“声明式、可验证实验”，而不是 GUI 或档案馆。

## X2｜可证伪研究 Agent

Agent 不只生成研究计划，而是维护：假设 → 可区分预测 → 计算实验 → 证据 → 修订。107 负责批量模拟或模型实验，Agent 负责选择下一项最有信息量的实验。

若放入算力赛道，它是 AI for Science application；若放入智能体赛道，它是科研支持 Agent。不能用同一作品两投，必须选定主价值和实现边界。

## X3｜限时算力生存协议

不只做 checkpoint，而是把四小时限时建模成 protocol：根据剩余时间、checkpoint 成本和当前进度，动态决定继续计算、保存、缩小任务还是终止；恢复后验证状态连续性。

它可以用概率模型或在线决策体现技术深度，但首版仍要限制任务类型。

# 四、自由发散后的初步观察

这不是 scorecard，只是方向性观察：

1. **最贴 107 的想法**通常拥有平台不可替代的闭环：提交、运行、测量、失败、恢复或大规模实验，而不只是把 CLI 包成网页。
2. **最像智能体产品的想法**应包含动态理解、工具选择、来源冲突、长期状态或多 Agent 协作；静态 FAQ + RAG 不足以形成竞争力。
3. **团队的独特组合**是数学/概率 + AI + 两位不同年级的计算机学生。若项目完全不需要概率、实验设计或严谨验收，团队的一部分比较优势会被浪费。
4. **AI-heavy 开发**适合接口清楚、验收可自动化的项目。越是三端大一统、权限复杂、需求模糊的系统，Agent 生成代码越多，集成债务越高。
5. 自由发散后仍不应立刻定题。下一轮应先继续补充团队自己的反应，再选择需要做竞品检索与低成本验证的方向。
