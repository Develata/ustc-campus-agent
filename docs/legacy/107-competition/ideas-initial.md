# 首轮想法整理

更新时间：2026-07-21

本文只整理团队已经提出的想法与初步论证，不代表最终选题或 Deve Hermes 的正式排序。

## 一、算力平台赛道

### A. 107 使用体验整合平台

**团队观点**

将现有 SSH、SFTP 与 CLI 能力整合为 desktop / Web / mobile 前端，通过脚本完成：

- 作业提交、状态与日志查看；
- 作业克隆与资源使用统计；
- 文件搜索、打包、上传下载；
- 环境、数据、结果和报告的一体化工作流。

**已有论证**

- 团队无法修改平台后端，运行效率优化与调度算法缺少数据和权限基础。
- 因而比起底层调度优化，降低使用门槛、整合信息和可视化操作更自然。

**待确认**

- desktop / Web / mobile 三端是否明显超出比赛周期；
- 哪一个端是实际用户主入口；
- 相比已有 107 WebShell、SSH/SFTP 客户端和 Slurm 面板，独特价值是什么；
- 只靠用户权限可稳定获得哪些状态、日志和资源指标。

### B. 可复现实验档案馆 + 检查点恢复

**团队观点**

围绕限时 GPU 会话或意外中断，保存应用级 checkpoint，并记录：

- 代码版本；
- 环境与依赖；
- 数据来源；
- 参数与随机状态；
- 资源消耗；
- 运行结果及比较信息。

重新申请资源后，工具匹配实验元数据和 checkpoint，引导或执行恢复。

**已知边界**

- 不能承诺跨资源释放保留 GPU 显存状态；可行的是由应用序列化模型权重、优化器状态、随机数状态和迭代位置。
- 首版应限定受支持的任务类型，例如 PyTorch 训练或具有显式状态的循环型 Python 任务，而不是声称任意程序无感恢复。

**团队报告、尚待独立核验**

- Students GPU 会话约四小时；
- 用户能看到剩余时间；
- 用户目录跨会话持久保存。

**待确认**

- 剩余时间是否可机器读取，还是只能由页面显示；
- 是否有可靠终止信号，或只能由客户端计时；
- checkpoint 写入耗时与剩余时间之间如何留安全裕量；
- 恢复到不同 GPU/节点/依赖环境时的兼容边界；
- 运行数据说明如何形成可量化证据。

### C. 数学演示 / 科学计算应用

**团队观点**

利用算力平台运行数学动画、科学计算模拟实验或交互演示。

**待确认**

- 具体学科问题和目标用户尚未确定；
- 必须证明 107 算力是必要条件，而非普通笔记本即可完成；
- 需要从“漂亮 demo”提升为有明确教学、科研或复现实验价值的产品。

### D. 绿色算力规划助手

**团队观点**

根据截止时间、资源需求和历史情况推荐资源规格与运行时段，减少空转与过度申请。

**当前风险判断**

它依赖队列历史、节点利用率、能耗或调度数据；团队目前可能只有用户侧和前端可见信息。若无官方数据支持，不宜作为主线。

## 二、智能体赛道

### E. 持久化计划与任务分割系统

**杨同学观点**

复杂任务后期容易偏离初始目标。应在执行前形成类似“建筑图纸”的任务可视化，由人补充细节，再拆分并分发给多个子 Agent；区别于一次性 plan mode，应允许运行中暴露问题后继续修订。

**Develata 的质疑**

- 如果计划最终仍是多段 prompt，精确性并未自动获得保证；
- 需要说明它和已有持久化 `docs/plan`、软件工程 workflow skill、任务派发及验收矩阵的本质差异。

**真正的待解变量**

- 产品对象是“计划文档编辑器”“任务图执行器”还是“Agent workflow verifier”；
- 如何表示任务依赖、验收条件、变更和 replay，而不是只生成更长 prompt；
- 如何用实验说明它比现有 planning/workflow harness 更晚跑偏或更易恢复；
- 哪些决策必须由人确认，哪些可以自动推进。

### F. “我的科大”个人校园智能体

**当前状态（2026-07-21）**

团队决定优先讨论该方向，但尚未最终定题、命名或进入实现。原定范围已经包含校园办事导航、校园变化监测、校园机会匹配与路径规划，并希望允许用户自主挂载 plugins。独立概念 brief 见 [`agent-track-concept.md`](agent-track-concept.md)。

**Develata 的观点**

相比通用 coding / assistant Agent，优先做贴近科大生活的个人 Agent：

- 以自然语言作为统一入口；
- 访问分散在学校各网站的公开信息；
- 补足“我的科大”等传统交互产品覆盖不到的服务，如 107 算力平台与词元计划；
- 主 Agent 接收请求，子 Agent 承担检索、整理或专项问答。

**价值假设**

校园信息和服务入口高度分散，传统 App 依赖固定菜单与人工维护；Agent 可按用户意图跨站检索和组织信息。

**待确认**

- 首版最小用户旅程是什么，不能只做“什么都能问”的泛化入口；
- 哪些来源是公开网页，哪些需要登录或授权；
- 如何处理网页时效、来源引用、冲突信息和失败回退；
- 是否允许二次开发开源 Agent 框架，以及许可证、原创性和作品贡献如何说明；
- 如何证明它优于搜索引擎、RAG chatbot 或现有校园应用。

**官方材料核对（2026-07-21）**

- 已检索赛事通知、FAQ 及 USTC 官方站内相关结果，未找到“允许/禁止开源二次开发”的明确专项说明。
- 通知要求作品由队伍独立设计、开发，禁止抄袭；使用的代码、模型和外部服务来源须合法合规；已公开并已获得商业价值的产品不得参赛。
- 当前只能保守推定：开源组件可作为依赖，但不能以换皮 fork 冒充原创作品。许可证、上游来源、团队原创模块和新增贡献必须可审计。
- 该推定不是官方答复；若候选依赖 Hermes、OpenClaw 等上游框架，应在定题前向赛道联系人书面确认。

### G. 任务级临时沙盒

**外部讨论报告中的技术方向**

为个人校园 Agent 提供短生命周期、最小权限、任务结束即销毁的代码执行环境；长期数据由独立存储管理，外部副作用通过受控 Tool Gateway 和用户确认完成。

候选 runtime 包括 rootless Podman、gVisor、Kata Containers 与 Firecracker；初稿倾向 rootless Podman。

**当前定位**

沙盒是支撑能力，不是用户价值主张本身。是否采用何种 runtime，必须服从实际部署环境与 threat model，不能先于产品任务定型。

**待确认**

- 比赛环境是否允许 rootless Podman、user namespaces 或其他隔离 runtime；
- 演示版是否真的需要执行任意代码；
- 若只做检索、整理和受控工具调用，是否可暂时不开放通用代码执行；
- 校园 Agent 的凭据、网络、内网访问与审计边界。

## 三、首轮结构判断

以下只是整理后的结构，不是最终推荐：

- 算力平台赛道目前形成四类候选：通用 UX 平台、实验档案与恢复、学科应用、资源规划。
- 团队对“实验档案与检查点恢复”表现出最明确的共同兴趣，且痛点较具体。
- 智能体赛道目前形成两条产品主线：复杂任务计划/执行治理、校园个人 Agent；沙盒属于后者可能需要的基础设施。
- “给算力平台套通用 Agent 框架”实现不难，但难度低不等于没有产品价值；真正竞争力取决于领域数据、权限边界、可靠性、评测和完整用户旅程。
- 两个赛道可以独立推进；若未来联动，应证明联动带来必要价值，而不是复用代码后包装成两个作品。

## 四、尚未对齐的信息

- 四人的时间预算和两个赛道的实际人员分工；除 Develata 外目前均待确认；
- 已有技术资产、可复用仓库与许可证状态；
- 比赛是否允许以及如何认定开源项目二次开发；
- 107 比赛分区、SSH 权限、持久目录和可观察信号的实测边界；
- 两个赛道各自最重要的目标用户与一条核心用户旅程。

## 五、已对齐的总体策略

- 采用主次项目策略：一条线冲决赛/高奖，另一条线保证完整提交。
- 主赛道暂不指定，待统一 scorecard 与低成本验证后决定。
- 实现采用 AI-heavy workflow；Codex、DeepSeek、Kimi、Claude 等 Agent 可承担大量机械实现，人类保留规划、审查与验收 authority。
- Agent 数量不视为免费工程容量。所有候选仍按人类可审查的 spec、集成面与验收成本估算。
